Suggested Improvements
1. Africa's Talking over Twilio for Uganda — AT has direct MTN/Airtel connections, much lower latency and cost in East Africa. I'll design the SMS adapter so it's swappable with one config change.

2. MTN MoMo + Airtel Money payment callbacks — The mock data shows method: "mobile_money_mtn". I'll add webhook receiver endpoints for both payment gateways so real payments can auto-reconcile. This is critical for Uganda.

3. Idempotency keys on all write operations — Especially payments. Prevents duplicate charges when mobile networks drop mid-request.

4. Separate Celery worker service — The docker-compose doesn't have it yet. I'll add it to docker-compose.local.yml.

5. Row-Level Security in Postgres — Each landlord can only ever see their own data. Rather than filtering in every query, I'll set app.current_landlord_id as a Postgres session variable and add RLS policies at the DB level. Belt-and-suspenders on top of app-layer auth.

6. pgcrypto for signature data — Lease signatures store signatureDataUrl (base64 PNG, potentially 50-200KB). Store these encrypted at rest using pgp_sym_encrypt.

7. GDPR anonymisation pipeline — The POST /tenants/{id}/anonymise endpoint needs to zero out PII fields deterministically. I'll implement an Anonymiser class that runs in a transaction and emits an GDPR_ERASURE_COMPLETED event.

8. Webhook-first notifications — Don't call external APIs synchronously in request path. Every notification goes through Celery → retry logic → delivery status webhook back.

9. Audit log as event sourcing (append-only) — Lease audit is required. I'll extend this pattern to payments and onboarding so you have a full history for compliance.

10. OpenAPI tag grouping + Swagger auth — Auto-generate docs with try-it-out working via bearer token.

Security & GDPR Checklist
 All endpoints require valid JWT — no anonymous access except onboarding token flow
 Role checks: landlord/manager can write; tenant read-only (their own data)
 landlord_id filter on every query — never leak cross-landlord data
 RLS policies in Postgres as second layer
 Signature data encrypted at rest (pgcrypto)
 GDPR erasure: anonymise() zeroes name, email, phone, NIN, replaces with REDACTED-{hash}
 gdpr_consent_at required before creating a tenant profile
 data_retention_until enforced by scheduled Celery task (auto-anonymise after period)
 Rate limiting: 100 req/min per IP, 1000 req/min per authenticated user
 idempotency_key UNIQUE constraint on payments table
 Audit log for all lease state transitions (append-only table)
 HTTPS enforced in production (nginx terminates TLS)
 Secrets via env vars only — never hardcoded
 CORS: explicit allow-list, no * in production
Questions before I start coding
1. Notifications — Twilio or Africa's Talking?
The .env.example has Twilio credentials. For Uganda (MTN/Airtel subscribers), Africa's Talking has better delivery rates and lower cost. Should I build adapters for both and let config decide, or stick with Twilio only for now?

2. Payment gateway integration depth?
The frontend records payments manually (user selects MTN/Airtel and enters a transaction reference). Should I:

(a) Just persist what the user submits (simple, works now), or
(b) Add webhook receivers for MTN MoMo API + Airtel Money API so payments auto-confirm?
Option (b) is the right long-term answer but adds 2–3 weeks of work. I'd suggest designing the schema for (b) but implementing (a) now.

3. Celery worker — same container or separate?
For local dev I'll add a worker service to docker-compose.local.yml. In production, do you want it as a separate service (recommended — scales independently) or bundled with the API container?

4. PDF templates — any existing brand design to follow?
For lease agreements I'll use Jinja2 + WeasyPrint. Should the PDF match the Crib brand (dark indigo, same fonts as the frontend), or is a clean legal-document style preferred?

5. Logto OIDC — is the Logto instance running locally or will I stub auth for now?
I'll implement real JWKS validation either way, but if Logto isn't running yet I'll add a DEV_BYPASS_JWT=true env flag that accepts any bearer token and returns a mock user — similar to how the frontend has NEXT_PUBLIC_MOCK_API=true.

Ready to start coding the moment you confirm (or override) these 5 questions. I'll begin with Sprint 1 (scaffolding) since that's independent of the answers, and can begin that now while you respond if you'd like.
